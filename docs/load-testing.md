# LifeCore Suite load testing

LifeCore load tests are Apache JMeter 5.6 plans intended for Azure Load Testing, part of Azure App Testing. They target the REST API directly, use only core JMeter components, and are parameterized with JMeter properties so the same scripts run locally and in Azure.

## Files

| Profile | JMeter plan | Azure Load Testing YAML | Purpose |
| --- | --- | --- | --- |
| `smoke` | `loadtests/jmeter/smoke.jmx` | `loadtests/smoke.yaml` | One user, one pass through health, API reads, and representative writes. |
| `uw` | `loadtests/jmeter/underwriter-journey.jmx` | `loadtests/underwriter-journey.yaml` | Underwriter dashboard/workbench journey with decision and requirement-order writes. |
| `csr` | `loadtests/jmeter/csr-policy-servicing.jmx` | `loadtests/csr-policy-servicing.yaml` | Read-heavy policy search/Policy 360 servicing journey with low-rate writes. |
| `peak` | `loadtests/jmeter/mixed-peak.jmx` | `loadtests/mixed-peak.yaml` | 60% CSR / 40% underwriter peak capacity test. |

CSV data lives under `loadtests/jmeter/data/` and is generated by:

```bash
python3 loadtests/scripts/generate-data.py
```

Azure Load Testing places uploaded configuration files next to the JMeter plan at run time, so the JMX files reference CSVs by base name only: `cases.csv`, `policies.csv`, and `owner-lastnames.csv`. The YAML files list those CSVs under `configurationFiles`.

## JMeter parameters

All plans use these JMeter properties:

| Property | Default in JMX/YAML | Meaning |
| --- | --- | --- |
| `protocol` | `http` in JMX, `https` in YAML | HTTP scheme. |
| `host` | `localhost` in JMX | Host name without scheme. |
| `port` | empty in JMX, `443` in YAML | Port. Leave empty to omit the port. |
| `threads` | profile-specific | Virtual users per engine. |
| `rampup` | profile-specific seconds | Thread ramp-up. |
| `duration` | profile-specific seconds | Scheduler duration. |
| `thinkScale` | `1` | Multiplier for 1-3 second think-time timers. |

HTTP headers include `Content-Type: application/json`, `Accept: application/json`, `X-Correlation-Id: ${__UUID()}`, and persona headers (`uw-dana` for underwriter journeys, `csr-jordan` for CSR journeys).

## Scenarios and sampler names

Sampler names are stable because Azure Load Testing failure criteria reference them.

### Smoke

Includes `GET health ready`, `GET personas`, `GET dashboard KPIs`, `GET worklist`, all case workbench reads (`GET case detail`, `GET case requirements`, `GET risk assessment`, `GET case summary`, `GET case notes`, `GET case chat`), representative writes (`POST order requirement`, `POST case note`, `POST case chat`, `POST decision`), policy searches/reads, and servicing writes (`PUT address change`, `POST loan quote`, `PUT beneficiaries`).

### Underwriter journey

Flow: `GET dashboard KPIs` → `GET worklist` (Task view, random page 1-5) → CSV `caseNumber` → `GET case detail` → `GET case requirements` → `GET risk assessment` → `GET case summary` → `GET case notes`. A 10% Throughput Controller runs `POST decision`; a 5% controller runs `POST order requirement`.

### CSR policy servicing

Flow: `GET policies search by policy prefix` and `GET policies search by owner last name` → `GET policy detail` → `GET policy coverages` → `GET policy beneficiaries` → `GET policy billing` → `GET policy values` → `GET policy transactions`. Low-rate writes are `PUT address change` (5%), `POST loan quote` (5%), and `PUT beneficiaries` (2%).

### Mixed peak

Two thread groups split `threads` with JMeter `__jexl3` math: 60% CSR policy servicing and 40% underwriter journey. `loadtests/mixed-peak.yaml` uses 2 engines and `threads=100`, for about 200 total virtual users.

## Failure criteria

The YAML files use Azure Load Testing `failureCriteria.clientMetrics` syntax, including request-specific criteria such as:

```yaml
failureCriteria:
  clientMetrics:
    - avg(responseTimeMs) > 700
    - percentage(error) > 1
    - 'GET worklist: p95(responseTimeMs) > 500'
    - 'POST decision: p95(responseTimeMs) > 800'
```

Targets align to the NFRs: read p95 < 500 ms, write p95 < 800 ms, and error rate < 1% at the peak profile. Smoke criteria are intentionally looser for pipeline gating.

## Run locally

Start the app locally, then run a plan. The script runs from the CSV directory so base-name CSV references resolve.

```bash
# Install JMeter if needed
brew install jmeter

# Defaults: localhost:5119, http, 5 threads, 60 seconds
loadtests/scripts/run-local.sh loadtests/jmeter/smoke.jmx

# Override properties
JMETER_THREADS=10 JMETER_DURATION=120 loadtests/scripts/run-local.sh loadtests/jmeter/csr-policy-servicing.jmx
```

Results are written under `loadtests/results/<plan>-<timestamp>/`.

## Run in Azure Load Testing with Azure CLI

Create or update a test from a YAML file:

```bash
az load test create \
  --load-test-resource "$LOAD_TEST_RESOURCE_NAME" \
  --resource-group "$AZURE_RESOURCE_GROUP" \
  --load-test-config-file loadtests/smoke.yaml \
  --env host="$WEB_APP_HOST" protocol=https port=443 threads=1 rampup=1 duration=60 thinkScale=1
```

Start a run:

```bash
az load test-run create \
  --load-test-resource "$LOAD_TEST_RESOURCE_NAME" \
  --resource-group "$AZURE_RESOURCE_GROUP" \
  --test-id lifecore-smoke \
  --display-name "LifeCore smoke $(date +%Y%m%d-%H%M%S)"
```

Use the matching YAML/test IDs for the other profiles: `lifecore-underwriter-journey`, `lifecore-csr-policy-servicing`, and `lifecore-mixed-peak`.

## GitHub Actions

`.github/workflows/load-tests.yml` is a reusable and manual workflow. Its `test_profile` input maps to a YAML file:

| Input | YAML |
| --- | --- |
| `smoke` | `loadtests/smoke.yaml` |
| `uw` | `loadtests/underwriter-journey.yaml` |
| `csr` | `loadtests/csr-policy-servicing.yaml` |
| `peak` | `loadtests/mixed-peak.yaml` |

Optional inputs:

- `target_slot` (for example, `staging`) points the test at an App Service deployment slot and collects App Service metrics from the slot resource (`Microsoft.Web/sites/slots`).
- `base_url` overrides the target host.

The host is passed to JMeter through the action's `env` input. Each run uploads a `load-test-results-<profile>[-<slot>]` artifact.

Where load tests run:

- **Stage gate:** add the `stage` label to a PR. `ci.yml` deploys it to the `staging` slot and runs all four profiles in sequence. Any profile that breaches its `failureCriteria` fails the `Stage gate` check, which blocks promotion. See [deployment.md](deployment.md#stage-gate-and-promotion).
- **After promotion:** `deploy-app.yml` runs the `smoke` profile against production after the slot swap.

## Before/after performance demo story

1. Deploy LifeCore with optimized queries disabled:

   ```bash
   az webapp config appsettings set \
     --resource-group "$AZURE_RESOURCE_GROUP" \
     --name "$WEB_APP_NAME" \
     --settings Perf__UseOptimizedQueries=false
   ```

2. Run `uw` or `peak` and capture the baseline. In Azure Load Testing, note `GET worklist` and `GET policies search by policy prefix` / `GET policies search by owner last name` p90/p95 latency.
3. Enable the optimized path:

   ```bash
   az webapp config appsettings set \
     --resource-group "$AZURE_RESOURCE_GROUP" \
     --name "$WEB_APP_NAME" \
     --settings Perf__UseOptimizedQueries=true
   ```

4. Re-run the same profile with the same load parameters.
5. Use Azure Load Testing **Compare** view. The intended story is a visible p90 drop for `GET worklist` and policy search, plus lower SQL DTU/CPU and App Service CPU in server-side metrics.

## Server-side metrics

The Azure Load Testing YAML files include `appComponents` and a `Metrics` reference identity. They use placeholder resource IDs in source control; `.github/workflows/load-tests.yml` resolves the deployed App Service, App Service Plan, Azure SQL Database, and Application Insights resource IDs and writes a generated YAML file before invoking `azure/load-testing`.

The configured metrics include App Service requests, HTTP 5xx, response time, CPU time, and memory working set; App Service Plan CPU/memory; Azure SQL CPU, data IO, connections, and deadlocks; and Application Insights request/dependency duration and counts. You can also configure these in the Azure portal under the load test's **App components** page.
